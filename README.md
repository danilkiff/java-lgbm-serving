# java-lgbm-serving

[![CI](https://github.com/danilkiff/java-lgbm-serving/actions/workflows/ci.yml/badge.svg)](https://github.com/danilkiff/java-lgbm-serving/actions/workflows/ci.yml)

Инференс обученной в Python модели LightGBM из Java через Panama FFM, с
нативными кодами причин SHAP и harness численного паритета.

Домен для модели - сессионный фрод / risk-based authentication (RBA).

## Проблема

> Может ли JVM исполнять инференс модели, обученной в Python, воспроизводить её
> оценки и выдавать объяснимые коды причин на каждое решение - и чего стоит
> граница языка по сравнению с той же схемой на Go?

## Цели

- воспроизвести на JVM битовый паритет оценок и SHAP contributions с эталоном на
Python, без единой строки нативного кода;
- доказать объяснимость через SHAP: на отклонение - код причины, доказуемо
связанный с решением (контракт объяснений - в [docs/DESIGN.md](docs/DESIGN.md),
"Результат");
- измерить цену перехода FFM против cgo на одной машине, одной модели и одном
входе.

Данные RBA синтетические, качество обучения вторично: модели достаточно не быть
абсурдной. Обучение живёт в репозитории эталонов, сюда приходят только его
артефакты.

## TLDR: результаты

Паритет с Python битово точный на одной сборке (holdout 4000):

- raw margin maxD `0`;
- SHAP maxD `0`;
- sum(contrib)=margin maxD `1.1e-14`;
- смен решения `0`;
- топ-3 кодов причин `0/4000`.

Граница языка не вносит расхождения. Дампы Java (FFM) и Go (cgo) на одной
`model.txt`, одном холдауте и одной машине совпадают полностью:

- raw margin maxD `0`, смен решения `0`;
- contributions maxD `0`;
- топ-3 кодов причин `0/4000`.

Быстродействие тоже совпадает в пределах единиц процентов: обе реализации
упираются в один нативный предиктор, а не в свой способ его вызвать.

- скоринг: Java `11.2` мкс против Go `11.5` мкс;
- SHAP: Java `451.6` мкс против Go `445.2` мкс, то есть ~40x от скоринга у обеих;
- пул на 12 потоков: Java `0.61` предсказаний/мкс против Go `0.71`;
- аллокации на скоринг: Java `0.12` Б против Go `16` Б - буферы обмена с нативной
стороной переиспользуются, и горячий путь не создаёт мусора.

Точка деградации у Java та же, что у Go: SHAP ~40x дороже скоринга. Изоляция
горячего пути её закрывает - p99 скоринга под насыщенной очередью explain `14.8`
мкс против `8.4` мкс вхолостую, при стоимости одного SHAP `439.3` мкс
(`HotPathIsolationTest`).

Конкуренция корректна: 32000 предсказаний из 64 потоков на 12 хэндлах, `0`
расхождений с однопоточным эталоном.

Провенанс: Apple M2 Pro (12 потоков), macOS 26.5.2, LightGBM 4.6.0,
Temurin JDK 25.0.4, Go 1.26.5, `make bench` в обоих репозиториях. Абсолютные
значения машинозависимы.

## Быстрый старт

Нужны uv, JDK 25 и рантайм OpenMP (Linux: libgomp; macOS: `brew install libomp`).

```sh
./run.sh          # библиотека, эталоны, тесты, бенчмарки
make              # список целей
```

Эталоны паритета берутся из релиза репозитория эталонов
(`make refs REFS=release:<tag>`) либо из чекаута (`make refs REFS=local:<path>`).
